# FARM WARS — TECH REQUIREMENTS

## 1) Цель документа

Этот документ задает технический фундамент проекта `Farm Wars` и является источником для генерации всех последующих ТЗ (
task specs) через ИИ-агента.

Главные цели:

- получить играбельный мультиплеерный 2D farm-sim прототип (desktop, Windows),
- научиться командной разработке с ИИ-агентами,
- обеспечить четкое разделение ответственности и минимальные блокировки между разработчиками.

Операционный контур проекта обязательно дополняется:

- `DECISIONS.md` — фиксация ключевых технических/процессных решений,
- `TASK_STATUS.md` — единая доска статусов ТЗ, checkpoints и блокеров,
- `AGENTS.md` — правила работы ИИ-агентов в репозитории,
- `docs/frontend/` — подробная документация веб-клиента (`web/`).

---

## 2) Обязательные ограничения и договоренности

- Платформа: только Windows (сервер и сборка; браузерный клиент — целевой UI).
- Формат: desktop и/или браузер; **основной клиент в разработке** — `web/` (Svelte + Vite).
- Рендер и UI: **браузер** (`web/`) + legacy Python (`pygame`, `client/`) до parity.
- Ядро игрового цикла (game loop): Python.
- Мультиплеер: псевдо-реалтайм, `join by code`, поддержка `2+` игроков.
- Обязателен одиночный режим.
- БД: SQLite.
- Главный приоритет: функциональность и играбельность, а не графика/музыка.
- Матч считается успешным, если его можно доиграть до победного условия без критических сбоев.

## 3) Техническое видение продукта

### 3.1 Суть игры

Игра — 2D пиксельный симулятор фермы с двумя ключевыми зонами:

- зона грядок (растения),
- зона загона (животные).

Игрок:

- ухаживает за сущностями (полив, кормление, лечение),
- перерабатывает ресурсы через "заводы",
- продает продукты,
- применяет PvP-саботаж и защитные способности,
- стремится первым выполнить цель матча.

### 3.2 Обязательные игровые механики MVP

- Базовый цикл: посадка/рост/уход -> сбор сырья -> переработка на заводах -> продажа.
- Контент MVP:
    - ~10 растений,
    - ~2 животных,
    - заводы: молочный, хлебобулочный, мясокомбинат.
- Случайные события: засуха, наводнение, землетрясение, болезни.
- PvP-шалости: мины, заражение, саботаж инфраструктуры воды.
- Защиты от шалостей:
    - превентивные (вакцинация/профилактика),
    - активные (например, сканер мин).
- Атаки по умолчанию скрыты от соперника.
- При смерти растение/животное исчезает.

### 3.3 Победа в матче (MVP)

Первое обязательное условие победы:

- первым произвести и получить в инвентарь целевой сложный продукт.

Дополнительные типы целей могут быть добавлены позже через декларативные сценарии.

## 4) Архитектура: Python + C++

### 4.1 Почему кросс-языковой подход подходит проекту

- Позволяет параллельную работу двух разработчиков на разных языках.
- Дает учебный кейс промышленной интеграции нативного модуля в Python.
- Позволяет вынести вычислительно-формализованные части в C++ без переписывания UI/сети.

### 4.2 Разделение ответственности

- `NIKITA_LEAD`:
    - архитектура модулей и контрактов,
    - правила протокола и data contracts,
    - ревью интеграций,
    - координация ТЗ и приемка чекпоинтов.
- `SANYA` (C++):
    - нативный модуль симуляции (`engine_core`),
    - детерминированные расчеты сущностей и эффектов,
    - API модуля для Python.
- `NIKITA` (Python + web):
    - веб-клиент (`web/`) — основной UI,
    - legacy клиент (`pygame`),
    - мультиплеерный клиентский слой (HTTP + sync),
    - серверная логика матча и загрузки данных из БД,
    - SQLite схема и сидирование контента.

### 4.3 Модульная структура репозитория (фактическая, 2026-05-28)

| Модуль | Owner | Ключевые артефакты |
|--------|-------|-------------------|
| `web/` | `NIKITA` | `src/lib/api`, `actions/gameActions.ts`, `sync/`, `components/` — см. [`docs/frontend/README.md`](docs/frontend/README.md) |
| `client/` | `NIKITA` | `main.py`, `net.py`, `sync_poller.py` (legacy) |
| `server/` | `NIKITA` | `main.py`, `http_api.py`, `game_server.py`, `match.py`, `tick_loop.py` |
| `db/` | `NIKITA` | `schema.sql`, `seed_minimal.sql`, `loader.py`, `pricing.py` |
| `shared/` | `NIKITA_LEAD` | `contracts.py` |
| `engine_cpp/` | `SANYA` | `simulate_tick.cpp`, `engine_core.cpp`, CMake |
| `engine_core_stub/` | интеграция | `stub.py` (тот же API, что C++) |
| `fixtures/` | общая | JSON для world/actions |
| `tools/` | общая | `init_db.py`, `test_*`, `smoke_test.py` |
| `docs/contracts/`, `docs/specs/` | `NIKITA_LEAD` | контракты и ТЗ |

### 4.4 Границы между Python и C++

Python управляет:

- game loop и тикером,
- сетевыми событиями,
- сохранением/загрузкой состояния,
- UI и UX.

C++ модуль отвечает за:

- применение игровых правил к состоянию мира за тик,
- расчет роста, болезней, влияния катастроф и саботажей,
- расчет стоимости/времени производства по входным параметрам.

Контракт обмена:

- Python формирует "snapshot + commands" для тика,
- передает в C++,
- получает "next_state + events".

Рекомендуемый транспорт между слоями:

- старт MVP: dict/list структуры Python, принимаемые pybind11,
- развитие: переход на компактные DTO (dataclass/pydantic-like contracts).

### 4.5 Интеграция C++ в Python

Обязательные решения:

- `pybind11` для биндинга C++ модуля,
- `CMake` для сборки,
- единая точка импорта в Python (`import engine_core`).

Обязательный ранний интеграционный чекпоинт:

- "Hello Tick": Python вызывает C++ функцию симуляции на тестовом состоянии и получает валидный результат.

## 5) Сетевая модель (MVP)

### 5.1 Тип мультиплеера

- Псевдо-реалтайм на тиках фиксированного интервала (по умолчанию **4 тика/сек**, `FARM_WARS_TICK_SEC=0.25`).
- Поля `*_sec` в мире и каталоге — **тики симуляции**, не wall-clock секунды (`shared/game_pacing.py`, DEC-014).
- Сервер — авторитетный источник истины.
- Клиенты отправляют команды (actions), не "готовое состояние".
- Поддержка **2–4 игроков** в одном матче; автотест: `tools/test_multiplayer.py`, спека `docs/specs/gameplay/009`.

### 5.2 Join flow (реализовано)

- Хост: `POST /api/matches/create` → `match_id`, `join_code`.
- Гости: `POST /api/matches/join` с `join_code` и `player_name`.
- Хост: `POST /api/matches/start` → tick loop, начальный `StateSyncEvent`.
- Игроки: `POST /api/matches/action` (`ClientActionEnvelope`).
- Клиенты: poll `GET /api/matches/{match_id}/sync?since_tick=N`.
- Гость в lobby: клиент poll до появления `world_state` после `start` (`client/main.py` `_poll_match_started`).
- Действия на клетке в движке: `owner_player_id == player_id` (`WATER_PLANT`, harvest, feed; см. `server/009`).

### 5.3 Транспорт MVP (DEC-010)

- Протокол: HTTP + JSON (`Content-Type: application/json`).
- Сервер: `FARM_WARS_HOST` (default `0.0.0.0`), `FARM_WARS_PORT` (default `8765`).
- Клиент: поля Server IP / Port в lobby, CLI `--host` / `--port`, env `FARM_WARS_SERVER*`.
- Health-check: `GET /api/health`.

### 5.4 Offline/Single mode

- Одиночный режим: один клиент + локальный сервер (`127.0.0.1`), Create → Start без второго игрока.
- Тот же server tick loop и `engine_core` / `engine_core_stub`.

### 5.5 LAN multiplayer

- Сервер на хосте слушает все интерфейсы; в лог выводится LAN IPv4 (`server/network_util.py`).
- Гость указывает IP хоста в клиенте. Требуется открытый порт в брандмауэре Windows.
- Sign-off сценарий: `docs/specs/gameplay/001.SIGNOFF_DEMO_SCRIPT.md` (2 и 3 игрока).
- Проверка MP: `docs/specs/gameplay/009.NIKITA.MULTIPLAYER_2PLUS_VERIFICATION.md`.

## 6) База данных и декларативный контент

### 6.1 Общие принципы

- SQLite — единственный обязательный storage для MVP.
- Схема должна быть нормализована и содержать FK.
- Игра читает продукты/рецепты/правила из БД при запуске.

### 6.2 Контент, который должен быть декларативным

- растения,
- животные,
- рецепты,
- заводы,
- случайные события,
- шалости и контрмеры,
- параметры экономики (включая коэффициенты формул).

### 6.3 Правила расчета цены продукта

Поле цены в рецепте:

- если `price_override` задан, используется он;
- если `price_override` = `NULL`, применяется формула по умолчанию (DEC-011):
    - `round((sum(base_sell_price × amount) + production_time_sec × buildings.time_coef) × 1.4)` (~+40% к базе),
    - где `time_coef` берётся из завода рецепта (`recipes.building_type` → `buildings`).

Реализация: `db/pricing.py`, `calculate_recipe_price`.

### 6.4 Мультиплеер и рецепты

- Сервер хранит и отдает игрокам единый набор рецептов матча (вариант A).
- Клиент не считается доверенным источником рецептов.
- Валидация "читерских" рецептов на MVP не обязательна.

## 7) Система экономики и производства

- Валюта одна: `Бестики`.
- Цены на рынке статические (MVP).
- Каждый завод производит одновременно только один item в своей очереди.
- Разные заводы могут работать параллельно.
- Скорость производства зависит:
    - от базового времени рецепта,
    - от уровня соответствующего завода.

## 8) Минимальные технические требования к качеству

- Код должен запускаться локально на Windows по понятным командам.
- Основные ошибки должны логироваться в консоль.
- Критические операции (матч-старт, тик, завершение рецепта, победа) должны быть покрыты базовыми проверками.
- Минимум автотестов допустим; приоритет — рабочий вертикальный срез.
- CI/CD, Docker, perf-метрики для MVP не обязательны.

## 9) Процесс постановки задач через ИИ-агента

Этот процесс обязателен для всех новых задач.

### Шаг 1. Идея задачи

Разработчик формулирует идею в свободной форме:

- что нужно сделать,
- зачем это нужно,
- какой ожидаемый результат.

### Шаг 2. Уточняющие вопросы от ИИ-агента

ИИ-агент изучает репозиторий и задает любое нужное число вопросов:

- по границам задачи,
- API/данным,
- UX/поведению,
- критериям приемки,
- влиянию на текущую архитектуру.

### Шаг 3. Ответы разработчика

Разработчик обязан ответить на все вопросы до генерации ТЗ.

### Шаг 4. Генерация ТЗ

ИИ-агент создает файл ТЗ с именованием по правилам раздела 10.
ТЗ обязательно включает секции из раздела 11.

### Шаг 5. Работа по чекпоинтам

В каждом ТЗ фиксируются checkpoints.
После выполнения каждого checkpoint ИИ-агент:

- останавливается,
- показывает результат,
- запрашивает приемку разработчика.

Переход к следующему checkpoint возможен только после подтверждения.

### Шаг 6. Фиксация решения и статуса

После каждого принятого checkpoint команда обязана:

- обновить статус задачи в `TASK_STATUS.md`,
- при наличии нового архитектурного/процессного выбора добавить запись в `DECISIONS.md`.

## 10) Правила именования файлов ТЗ

### 10.1 Формат имени файла

Обязательный формат:

`{n3}{n2}{n1}.{DEVELOPER}.{TITLE}.md`

Где:

- `{n3}{n2}{n1}` — трехзначный индекс (`001`, `002`, ...),
- `{DEVELOPER}` — один из:
    - `NIKITA`,
    - `SANYA`,
    - `NIKITA_LEAD`,
- `{TITLE}` — короткое имя в `UPPER_SNAKE_CASE` на латинице.

Примеры:

- `001.NIKITA.CLIENT_LOBBY_FLOW.md`
- `002.SANYA.CPP_TICK_ENGINE_BASE.md`
- `003.NIKITA_LEAD.NETWORK_CONTRACT_V1.md`

### 10.2 Правила нумерации

- Индексация ведется отдельно по каждой секции в `docs/specs/`.
- Секции задаются папками (например, `gameplay`, `network`, `db`, `client`, `engine_cpp`).
- Внутри секции номера возрастают монотонно без переиспользования.

## 11) Обязательный шаблон ТЗ

Каждый файл ТЗ обязан содержать:

1. `Context`  
   Что уже есть в репозитории и почему задача нужна.

2. `Goal`  
   Измеримый конечный результат.

3. `Scope`  
   Что входит и что явно не входит.

4. `Functional Requirements`  
   Поведенческие требования (списком, с приоритетами при необходимости).

5. `Non-Functional Requirements`  
   Ограничения по платформе, стабильности, совместимости, UX-отклику и т.п.

6. `Data Contracts / API Contracts`  
   Форматы структур, ключевые поля, типы команд, ограничения.

7. `Implementation Plan`  
   Пошаговый план реализации.

8. `Checkpoints`  
   Контрольные точки приемки:
    - что именно должно быть готово,
    - как это проверить,
    - какой артефакт показать (лог, скрин, файл, демо-поток).

9. `Acceptance Criteria`  
   Четкие критерии "задача выполнена".

10. `Test Plan`  
    Минимальные проверки вручную/автоматически для подтверждения результата.

## 13) Изолированная разработка без тестовых данных

Цель: каждый разработчик может полноценно двигаться по своей зоне, даже если соседний модуль еще не готов.

### 13.1 Принцип Contract-First

Перед началом реализации любой межмодульной задачи обязательно создаются:

- контракт данных (структуры, поля, типы, обязательность),
- контракт команд/событий (кто что отправляет и что получает),
- версия контракта (`v1`, `v2` и т.д.).

Контракты хранятся в:

- `docs/contracts/` (читаемое описание),
- `shared/` (машиночитаемые DTO/схемы).

### 13.2 Обязательные стаб-артефакты

Для каждой зоны должны быть заглушки:

1. **C++ зона (`SANYA`)**
    - `engine_core_stub` для Python:
        - принимает snapshot,
        - возвращает deterministic mock `next_state + events`.

2. **Python server зона (`NIKITA`)**
    - `server_stub`:
        - принимает клиентские actions,
        - отдает mock state sync и тик-события.

3. **DB зона (`NIKITA`)**
    - `seed_minimal.sql`:
        - минимальный набор сущностей для локальной отладки,
        - фиксированный и воспроизводимый.

### 13.3 Наборы тестовых фикстур

Каждая функция, затрагивающая внешний модуль, обязана иметь fixtures:

- `fixtures/world_state/*.json`
- `fixtures/actions/*.json`
- `fixtures/recipes/*.json`

Требования к fixtures:

- маленькие и читаемые,
- детерминированные (без случайных значений),
- с версией контракта в метаданных.

### 13.4 Вертикальные integration slices

Вместо ожидания полного функционала команда делает короткие вертикальные срезы:

- Slice A: загрузка мира -> тик -> отрисовка.
- Slice B: рецепт -> производство -> начисление валюты.
- Slice C: join by code -> 1 действие игрока -> серверный апдейт.

Каждый slice должен работать как на реальных модулях, так и на заглушках.

### 13.5 Правило независимой готовности задачи

Задача считается "готова к разработке", если:

- есть контракт,
- есть минимум 1 fixture,
- есть соответствующий stub/adapter,
- прописан способ локальной проверки без соседнего разработчика.

Без этих условий задача в работу не берется.

## 15) Definition of Done для MVP

MVP считается готовым, если:

- на Windows запускается клиент и сервер,
- доступен одиночный режим,
- доступен мультиплеер **2–4** с входом по коду (`test_multiplayer.py` зелёный),
- можно сыграть полноценный матч до победы по целевому продукту,
- работают растения, животные, заводы, рецепты, случайные события и PvP-шалости/защиты,
- игровые данные загружаются из SQLite (с FK и нормализованной схемой),
- ключевые задачи оформляются и ведутся через ТЗ по правилам этого документа,
- разработка каждой межмодульной задачи возможна изолированно через контракты, fixtures и stubs.
