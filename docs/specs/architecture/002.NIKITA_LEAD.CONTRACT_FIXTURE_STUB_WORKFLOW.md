# Context

Команда хочет работать параллельно, даже когда соседние модули не готовы. Для этого нужен стандартный workflow
`contract -> fixture -> stub -> integration`.

# Goal

Внедрить обязательный процесс изолированной разработки и подготовить минимальный каркас артефактов для всех будущих ТЗ.

# Scope

In scope:

- структура `docs/contracts` и `fixtures/*`,
- правила версионирования fixtures,
- базовые stubs для client/server/engine интеграций,
- критерий "задача готова к старту".

Out of scope:

- реализация боевой логики модулей,
- полные тестовые сценарии всех механик.

# Functional Requirements

- Создать и описать структуру:
    - `docs/contracts/`,
    - `fixtures/world_state/`,
    - `fixtures/actions/`,
    - `fixtures/recipes/`.
- Зафиксировать формат метаданных fixture:
    - `fixture_id`,
    - `contract_version`,
    - `description`.
- Описать обязательные stub-режимы:
    - `engine_stub`,
    - `server_stub`,
    - `db_seed_minimal`.
- Внедрить критерий readiness:
    - нет контракта/fixture/stub -> задача не стартует.

# Non-Functional Requirements

- Workflow должен быть коротким и практичным для новичков.
- Любой новый участник должен понять схему за 10 минут.
- Артефакты должны быть переиспользуемы между ТЗ.

# Data Contracts / API Contracts

- Fixtures обязаны соответствовать `GAME_CONTRACTS_V1`.
- Любое расхождение fixture и контракта считается дефектом.
- Stub-интерфейсы должны совпадать с интерфейсами будущих real-модулей.

# Implementation Plan

1. Подготовить дерево папок артефактов.
2. Описать формат fixture и naming convention.
3. Описать обязательные точки включения stub-режима.
4. Добавить это как обязательный блок в новые межмодульные ТЗ.

# Checkpoints

1. **Artifacts Layout Approved**
    - Артефакт: структура папок контрактов/fixtures.
    - Проверка: каркас готов к использованию в любых задачах.
2. **Fixture Spec Approved**
    - Артефакт: спецификация формата fixture.
    - Проверка: можно создать и валидировать fixture без двусмысленности.
3. **Stub Policy Approved**
    - Артефакт: правила для stub-режимов.
    - Проверка: любая команда может продолжать разработку без ожидания соседа.
4. **Process Embedded Approved**
    - Артефакт: шаблон требования в ТЗ.
    - Проверка: новые межмодульные ТЗ включают блок изолированной разработки.

# Acceptance Criteria

- Workflow formalized и принят командой.
- Есть готовый каркас артефактов для изолированной разработки.
- Следующие ТЗ можно запускать без блокировок по данным/интеграции.

# Test Plan

- Создать пробный fixture по спецификации и проверить совместимость с контрактом.
- Запустить один сценарий через stub вместо реального модуля.
- Проверить, что новый ТЗ-шаблон содержит требования к contract/fixture/stub.
