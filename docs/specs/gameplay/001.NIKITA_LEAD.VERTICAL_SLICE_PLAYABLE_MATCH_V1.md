# Context

У команды есть отдельные направления разработки, но нужен общий "сквозной" критерий, что игра уже реально работает как
матч, а не как набор изолированных модулей.

# Goal

Собрать первый играбельный вертикальный срез: от входа в матч до победы по целевому продукту в режиме 2+ игроков.

# Scope

In scope:

- интеграция client + server + db + engine/stub,
- минимум один полный матчевый сценарий,
- победа по целевому продукту.

Out of scope:

- полный контент (10 растений и т.д.),
- сложные PvP-шалости,
- расширенная балансировка.

# Functional Requirements

- Матч создается и доступен по join-коду.
- Два игрока подключаются и получают синхронное состояние.
- Игроки могут выполнить базовый фермерский цикл:
    - произвести сырье,
    - запустить рецепт,
    - получить продукт.
- Сервер отслеживает прогресс и объявляет победителя.
- Клиенты видят завершение матча.

# Non-Functional Requirements

- Сценарий должен быть воспроизводим на чистом локальном окружении Windows.
- Допускается LAN: гость подключается по IP хоста (см. `README.md`).
- В процессе матча не допускаются критические падения сервера/клиента.
- При недоступности C++ ядра допускается stub, но контракт должен быть тем же.

# Baseline готовности (2026-05-28)

Модули `db/001`, `server/001`, `client/001`, `engine_cpp/001` — **DONE**.  
Сквозной сценарий для sign-off `gameplay/001`:

1. `py tools/init_db.py --seed`
2. `py -m server` (хост)
3. Клиент 1: Create → Start, передать join code
4. Клиент 2 (опц. LAN IP): Join
5. `W` полив, `B` рецепт `bread`, дождаться победы

Автотесты: `test_server_flow.py`, `test_client_net.py` (сервер запущен).

# Data Contracts / API Contracts

- Используются только `v1` контракты.
- В вертикальном срезе обязателен фиксированный fixture-сценарий матча.
- Победное событие передается отдельным `ServerEvent`.

# Implementation Plan

1. Собрать список зависимостей модулей и контрактов.
2. Подготовить fixture состояния "начало матча".
3. Интегрировать клиент и сервер по join/tick/action.
4. Подключить engine_core или engine_stub.
5. Пройти полный сценарий до победы и зафиксировать артефакты.

# Checkpoints

1. **Integration Baseline Approved**
    - Артефакт: рабочий запуск всех слоев.
    - Проверка: клиент подключается к серверу, сервер читает данные из БД.
2. **Playable Loop Approved**
    - Артефакт: базовый gameplay loop в матче.
    - Проверка: игроки совершают действия и получают обновления состояния.
3. **Win Flow Approved**
    - Артефакт: победное событие и завершение матча.
    - Проверка: матч завершается корректно для всех подключенных клиентов.
4. **Demo Ready Approved**
    - Артефакт: короткий воспроизводимый сценарий для показа.
    - Проверка: команда может повторить матч "с нуля" по шагам.

# Acceptance Criteria

- Есть рабочий сквозной сценарий 2+ игроков.
- Матч завершается по целевому продукту.
- Сборка не зависит от ручных патчей "на месте".
- Документированы команды запуска и проверок.

# Test Plan

- Ручной прогон двумя клиентами на localhost.
- Проверка события победы и корректного завершения.
- Повторный прогон с теми же fixture-данными на чистом окружении.
- Проверка fallback-режима со stub движком (если C++ еще в работе).
