# Context

После `db/001`, `server/001–002`, `client/001` и `engine_cpp/002.SANYA` команда имеет рабочий
вертикальный прототип: join → матч → полив → посадка → печь → победа по `bread`.

Однако цикл фермы пока **неполный и хрупкий** для демо и обучения:

| Проблема | Сейчас |
|----------|--------|
| Семена | Только стартовый инвентарь из fixture; нельзя докупить |
| Рецепт | Клиент передаёт `duration_sec` вручную — не из SQLite |
| UI | Мало обратной связи (`PLANT_PLACED`, инвентарь, ошибки движка) |
| Посадка | В клиенте захардкожен `plant_id = wheat` |
| Магазин | Нет действия «купить» — экономика не замкнута |

Это ТЗ описывает **следующий играбельный слой** в зоне `NIKITA` (client + server + контракты),
без изменений C++ движка (`SANYA`), если не согласовано отдельно.

# Goal

Сделать воспроизводимый **полный мини-цикл фермы** в матче:

**купить семена → посадить → полить → запустить рецепт из БД → получить продукт → победить**,

с понятным UI и серверной авторитетностью данных из SQLite.

# Scope

## In scope

### Сервер (`NIKITA`)

- Новое действие `BUY_PRODUCT`: списание `money_bestiki`, начисление в `inventory` (логика на сервере, без C++).
- Обогащение `START_RECIPE` перед `simulate_tick` (как `PLACE_ON_TILE` в `server/002`):
  - клиент шлёт `{factory_id, recipe_id}`;
  - сервер подставляет `duration_sec` из `catalog.recipes`;
  - проверка: рецепт существует, `recipe.building_type` совпадает с `factory.factory_type`.
- Валидация покупки: достаточно денег, продукт есть в `products`, для семян — `plant_id` существует в `plants`.
- Ошибки покупки/рецепта → `ServerEvent` `CONTRACT_ERROR` или `PURCHASE_FAILED` / `RECIPE_REJECTED` (см. контракты ниже).

### Клиент (`NIKITA`)

- Панель магазина в экране матча: купить семена (`wheat`, `corn`, `potato`) по цене из каталога (через API или sync после покупки).
- Выбор семени для посадки: не только `wheat` — по наличию в инвентаре (минимум: циклический выбор `1/2/3` или кнопки).
- HUD: деньги, инвентарь (топ-5 позиций), последние 5 событий с сервера, явное сообщение при `MATCH_FINISHED`.
- `START_RECIPE` без `duration_sec` в payload.
- `BUY_PRODUCT` с клавиши/кнопки.

### Контракты / документация

- Обновить `GAME_CONTRACTS_V1.md`: новые `action_type` / `event_type`.
- Запись в `DECISIONS.md` при принятии.
- Строка в `TASK_STATUS.md`.

## Out of scope

- Полный магазин UI (категории, скролл, иконки) — только минимальные кнопки.
- Продажа урожая с грядки (только покупка семян и рецепты).
- Животные, PvP, случайные события в матче.
- Изменения `engine_cpp` (рост растений по тикам, сбор урожая) — отдельные ТЗ `SANYA`.
- Новые таблицы SQLite — использовать `products`, `plants`, `recipes` как есть.
- WebSocket — остаётся HTTP poll.

# Functional Requirements

## FR-1: Покупка продукта (`BUY_PRODUCT`)

1. Клиент отправляет `PlayerAction`:
   - `action_type`: `"BUY_PRODUCT"`
   - `payload`: `{ "product_id": string, "amount": number }` (`amount` >= 1, default 1).

2. Сервер **до** вызова `simulate_tick` (или в отдельной фазе того же тика) обрабатывает покупку:
   - Находит игрока по `action.player_id`.
   - Цена единицы = `products.base_sell_price` (MVP: покупка по той же цене, что «базовая продажа»; формула магазина — позже).
   - Итого: `total = base_sell_price * amount`.
   - Если `money_bestiki < total` → событие `PURCHASE_FAILED` с `{reason: "NOT_ENOUGH_MONEY", ...}`.
   - Иначе: `money_bestiki -= total`, инвентарь += `amount`.
   - Успех → событие `PRODUCT_PURCHASED` с `{product_id, amount, total_paid, player_id}`.

3. Для `product_id`, который является `plants.plant_id` (семена), покупка разрешена.
   Для произвольных `PROCESSED` без plant-записи — разрешена, если есть в `products` (на будущее).

## FR-2: Обогащение `START_RECIPE` на сервере

1. Клиент шлёт только:
   ```json
   { "factory_id": "p1_bakery_1", "recipe_id": "bread" }
   ```

2. Сервер (`action_enricher.py`, расширение):
   - Загружает `recipe = catalog.recipes[recipe_id]`.
   - Если нет → `CONTRACT_ERROR` / не передавать в движок.
   - Проверяет `factory.factory_type == recipe.building_type`.
   - Подставляет `duration_sec = recipe.production_time_sec`.
   - Передаёт в движок полный payload (как сейчас ожидает `START_RECIPE`).

3. Клиент **не** отправляет `duration_sec` (удалить из `client/main.py`).

## FR-3: Клиент — магазин и посадка

1. В match UI — блок «Магазин» (правая панель или под HUD):
   - Кнопки: `Buy wheat (5)`, `Buy corn (6)`, `Buy potato (4)` — цены из последнего `world_state` не видны без каталога на клиенте;
     **MVP:** захардкодить цены в UI с комментарием «дублирует seed» ИЛИ добавить `GET /api/catalog` (опционально, см. FR-6).

2. **Рекомендация MVP:** цены на кнопках из констант клиента, совпадающих с `seed_minimal.sql`; сервер всё равно авторитетен при списании.

3. Посадка (`T`):
   - Использовать «выбранное семя»: по умолчанию первое доступное в инвентаре из списка `wheat`, `corn`, `potato`.
   - Клавиши `1`/`2`/`3` — выбор типа семян перед посадкой (опционально, но желательно в CP3).

## FR-4: Клиент — обратная связь

1. HUD показывает:
   - `money_bestiki`;
   - инвентарь (все позиции с `amount > 0`);
   - последние N событий (`PLANT_PLACED`, `PLANT_WATERED`, `RECIPE_STARTED`, `RECIPE_FINISHED`, `PRODUCT_PURCHASED`, `PURCHASE_FAILED`, `CONTRACT_ERROR`).

2. При `MATCH_FINISHED` — overlay или яркая строка: победитель + целевой продукт.

## FR-5: Стартовый инвентарь (уточнение)

- Сохранить небольшой стартовый набор из fixture (как сейчас) **или** уменьшить до `wheat x1` для принуждения к покупке.
- **Решение для реализации:** оставить `wheat x3, corn x1` (меньше рефакторинга); демо-сценарий всё равно может включать покупку `potato`.

## FR-6 (опционально, checkpoint 5): `GET /api/catalog`

- Отдавать клиенту срез: `products`, `plants` (id + display_name + price), `recipes` (id + building + time).
- Позволяет рисовать магазин без хардкода.
- Если не успеваем — FR-3 с константами, checkpoint помечается как пропущенный.

# Non-Functional Requirements

- Покупка и обогащение рецепта — детерминированы на сервере.

- Изменения только в зонах `NIKITA` (`client/`, `server/`, `docs/contracts/`, `tools/`).

# Data Contracts / API Contracts

Версия контракта: `v1` (расширение в рамках v1 — только новые строковые типы).

## Новый `PlayerAction`: `BUY_PRODUCT`

```json
{
  "contract_version": "v1",
  "player_id": "p1",
  "action_type": "BUY_PRODUCT",
  "payload": {
    "product_id": "wheat",
    "amount": 1
  },
  "client_ts": 1710000000000
}
```

Обрабатывается **сервером**, не передаётся в `engine_cpp`.

## Изменённый клиентский `START_RECIPE` (минимальный payload)

```json
{
  "action_type": "START_RECIPE",
  "payload": {
    "factory_id": "p1_bakery_1",
    "recipe_id": "bread"
  }
}
```

Обогащённый payload для движка (сервер → engine, без изменений движка):

```json
{
  "factory_id": "p1_bakery_1",
  "recipe_id": "bread",
  "duration_sec": 30
}
```

## Новые `ServerEvent`

### `PRODUCT_PURCHASED`

```json
{
  "event_type": "PRODUCT_PURCHASED",
  "server_tick": 12,
  "payload": {
    "player_id": "p1",
    "product_id": "wheat",
    "amount": 1,
    "total_paid": 5
  }
}
```

### `PURCHASE_FAILED`

```json
{
  "event_type": "PURCHASE_FAILED",
  "server_tick": 12,
  "payload": {
    "player_id": "p1",
    "product_id": "wheat",
    "reason": "NOT_ENOUGH_MONEY",
    "required": 5,
    "available": 3
  }
}
```

### `RECIPE_REJECTED` (опционально, если рецепт не прошёл валидацию на сервере)

```json
{
  "event_type": "RECIPE_REJECTED",
  "server_tick": 12,
  "payload": {
    "player_id": "p1",
    "factory_id": "p1_bakery_1",
    "recipe_id": "cake",
    "reason": "WRONG_BUILDING_TYPE"
  }
}
```

## Зависимости от существующих контрактов

- `PLACE_ON_TILE` — без изменений (`server/002`, `002.SANYA`).
- `StateSyncEvent`, `ClientActionEnvelope` — без изменений структуры обёрток.
- `GAME_CONTRACTS_V1.md` — дополнить перечисления типов после реализации.

# Implementation Plan

## Этап 1 — Сервер: покупка

1. `server/shop.py` — `process_buy_product(action, world_state, catalog) -> (world_mutations, events)`.
2. В `Match.process_tick`: разделить очередь на `engine_actions` и `server_only_actions`:
   - `BUY_PRODUCT` → `shop.py`;
   - остальное → `enrich_actions_for_tick` → `simulate_tick`.
3. Тесты: `test_buy_product_ok`, `test_buy_not_enough_money` в `tools/test_server_flow.py`.

## Этап 2 — Сервер: обогащение рецепта

1. Расширить `server/action_enricher.py`: `enrich_start_recipe`, вызывать из `enrich_actions_for_tick`.
2. Убрать зависимость от клиентского `duration_sec`.
3. Тесты: успешный bread, неверный building, неизвестный recipe_id.

## Этап 3 — Клиент: магазин и посадка

1. `client/main.py`: кнопки покупки / клавиши; `_send_buy`, `_send_recipe` без duration.
2. Выбор семени для `_send_place`.
3. Расширить `_draw_hud` — инвентарь и события.

## Этап 4 — Контракты и документация

1. `GAME_CONTRACTS_V1.md`, `DECISIONS.md`, `TASK_STATUS.md`, `README.md` (кратко).

## Этап 5 (опционально) — `GET /api/catalog`

1. `server/http_api.py` + `game_server.get_catalog_snapshot()`.
2. Клиент: загрузка при входе в матч для цен на кнопках.

# Checkpoints

## CP-1: Server Buy Approved

- **Артефакт:** `server/shop.py`, интеграция в `match.py`.
- **Показать:** тесты покупки; в sync — `PRODUCT_PURCHASED`, деньги уменьшились, инвентарь вырос.
- **Проверка:** `py tools/test_server_flow.py` (новые кейсы buy).

## CP-2: Server Recipe Enrich Approved

- **Артефакт:** расширенный `action_enricher.py`.
- **Показать:** клиентский payload без `duration_sec`; движок получает `duration_sec` из БД.
- **Проверка:** тест `START_RECIPE` bread `production_time_sec=30` из seed.

## CP-3: Client Shop And Plant Approved

- **Артефакт:** UI магазина + посадка не только wheat.
- **Показать:** ручной сценарий: купить potato → посадить на пустую клетку.
- **Проверка:** `PLANT_PLACED` в HUD; инвентарь обновился после покупки.

## CP-4: Client HUD Approved

- **Артефакт:** HUD с деньгами, инвентарём, лентой событий.
- **Показать:** скрин/описание после полива, покупки, печки, победы.
- **Проверка:** все ключевые `event_type` видны игроку.

## CP-5 (опционально): Catalog API Approved

- **Артефакт:** `GET /api/catalog`.
- **Проверка:** клиент рисует цены без хардкода.

# Acceptance Criteria

- Игрок может **купить** семена в матче и **посадить** их на пустую клетку.
- Игрок может **запустить рецепт** без указания времени на клиенте; время берётся из SQLite.
- Полный сценарий до победы проходит в **singleplayer** и **2-player LAN** без падений.
- Автотесты сервера покрывают покупку и обогащение рецепта.
- Контракты v1 документированы; чужие зоны (`engine_cpp`) не изменены без согласования.

# Risks and Open Questions

1. **Цена покупки = `base_sell_price`?**  
   Для MVP — да. Отдельная колонка `buy_price` — вне scope.

2. **Покупка в том же тике, что и движок?**  
   Рекомендация: обрабатывать `BUY_PRODUCT` на сервере в начале `process_tick`, затем engine actions — игрок видит семена до посадки в следующем тике.

3. **Нужен ли `GET /api/catalog`?**  
   Желательно, но CP-5 опционален; без него — константы цен в клиенте.

4. **Подтверждение от `NIKITA_LEAD`:** новые `event_type` в v1 (не ломают forward compatibility).
