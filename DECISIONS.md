# DECISIONS LOG

Журнал архитектурных и процессных решений проекта `Farm Wars`.

Назначение:

- фиксировать "почему" по ключевым решениям,
- снижать повторные обсуждения одних и тех же вопросов,
- упрощать онбординг и ревью для команды.

---

## Как заполнять

Каждое решение добавляется новым блоком в конец файла.

Обязательный шаблон:

### DEC-XXX: Краткое название

- **Дата**: YYYY-MM-DD
- **Статус**: Proposed | Accepted | Superseded
- **Контекст**: какая проблема или выбор стоял
- **Решение**: что выбрано
- **Альтернативы**: что рассматривалось
- **Последствия**: плюсы/минусы выбранного варианта
- **Связанные ТЗ**: ссылки на файлы в `docs/specs/`

## Принятые решения

### DEC-001: Кросс-языковая архитектура Python + C++

- **Дата**: 2026-05-27
- **Статус**: Accepted
- **Контекст**: у команды разные сильные языки (Python и C/C++) и цель параллельной работы.
- **Решение**: Python отвечает за client/server/game loop; C++ — за simulation core через `pybind11`.
- **Альтернативы**: только Python; только C++.
- **Последствия**:
    - плюс: параллельная разработка по зонам ответственности;
    - плюс: учебный промышленный кейс интеграции;
    - минус: выше сложность сборки и контрактов.
- **Связанные ТЗ**:
    - `docs/specs/architecture/001.NIKITA_LEAD.ARCHITECTURE_CONTRACTS_V1.md`
    - `docs/specs/engine_cpp/001.SANYA.CPP_ENGINE_CORE_PYBIND_BASE.md`

### DEC-002: Мультиплеер server-authoritative и join-by-code

- **Дата**: 2026-05-27
- **Статус**: Accepted
- **Контекст**: нужен реализуемый MVP мультиплеера без сложного matchmaking.
- **Решение**: псевдо-реалтайм на тиках, сервер авторитетен, вход по коду комнаты.
- **Альтернативы**: peer-to-peer, браузерный формат, сложный матчмейкинг.
- **Последствия**:
    - плюс: проще контролировать честность и консистентность;
    - плюс: быстрее реализуется для практики;
    - минус: серверный слой обязателен даже для простых сценариев.
- **Связанные ТЗ**:
    - `docs/specs/server/001.NIKITA.SERVER_MATCH_JOIN_AND_TICK_LOOP.md`
    - `docs/specs/client/001.NIKITA.CLIENT_PYGAME_CORE_AND_MATCH_UI.md`

### DEC-003: Декларативный контент в SQLite

- **Дата**: 2026-05-27
- **Статус**: Accepted
- **Контекст**: нужно легко добавлять контент без переписывания кода.
- **Решение**: рецепты/сущности/параметры экономики грузятся из SQLite с нормализованной схемой и FK.
- **Альтернативы**: захардкоженные словари в коде; JSON-only без реляционных связей.
- **Последствия**:

    - плюс: меньше изменений в коде при балансировке;
    - минус: нужен качественный seed и контроль схемы.
- **Связанные ТЗ**:
    - `docs/specs/db/001.NIKITA.SQLITE_SCHEMA_AND_SEED_MINIMAL.md`

### DEC-006: Инструменты и окружение для engine_cpp (SANYA)

- **Дата**: 2026-05-27
- **Статус**: Accepted
- **Контекст**: нужно зафиксировать конкретные версии инструментов для C++ сборки, чтобы избежать "на моей машине не собирается".
- **Решение**:
    - Компилятор: MSVC 2022 (Visual Studio 2022).
    - Python: 3.13.
    - pybind11: установка через `pip install pybind11`, интеграция через `find_package(pybind11)` в CMake.
- **Альтернативы**: MinGW/MSYS2; vcpkg; FetchContent.
- **Последствия**:
    - плюс: pip-установка pybind11 проще для новичков, не требует ручного клонирования;
    - минус: привязка к MSVC (пока Windows-only, это не проблема).
- **Связанные ТЗ**:
    - `docs/specs/engine_cpp/001.SANYA.CPP_ENGINE_CORE_PYBIND_BASE.md`

### DEC-007: Создание shared/ DTO и engine_core_stub параллельно с C++ модулем

- **Дата**: 2026-05-27
- **Статус**: Accepted
- **Контекст**: GAME_TECH_REQUIREMENTS.md требует stub для каждой зоны и общие DTO в shared/. Принято решение делать их сразу на CP1, а не откладывать.
- **Решение**:
    - `shared/` создается сразу с Python-классами для контрактов v1 (TickInput, TickResult, WorldState, etc.).
    - `engine_core_stub` создается сразу как Python-заглушка, повторяющая интерфейс C++ модуля — для отладки NIKITA пока C++ модуль не готов.
- **Альтернативы**: отложить до следующих checkpoint; обойтись без stub.
- **Последствия**:
    - плюс: NIKITA может сразу начинать server/client разработку на stub;
    - плюс: контракты зафиксированы в коде, а не только в документах;
    - минус: чуть больше начальной работы на CP1.
- **Связанные ТЗ**:
    - `docs/specs/engine_cpp/001.SANYA.CPP_ENGINE_CORE_PYBIND_BASE.md`
    - `docs/specs/architecture/002.NIKITA_LEAD.CONTRACT_FIXTURE_STUB_WORKFLOW.md`

### DEC-008: Защита зон ответственности — ИИ предупреждает о выходе за границы роли

- **Дата**: 2026-05-28
- **Статус**: Accepted
- **Контекст**: чтобы избежать случайного вмешательства в чужую зону, ИИ-агент должен предупреждать разработчика, если его запрос выходит за границы его роли.
- **Решение**: если разработчик просит сделать что-то, что по модульной структуре принадлежит другому участнику, ИИ обязан:
    - явно сказать: «Это зона [NIKITA | NIKITA_LEAD | SANYA], не [имя запросившего].»
    - уточнить: «Точно продолжаем?»
    - без подтверждения не выполнять.
- **Альтернативы**: молча делать что просят; молча отказывать.
- **Последствия**:
    - плюс: меньше хаоса и пересечений в коде;
    - плюс: разработчики осознанно принимают решения о выходе за свою зону;
    - минус: чуть больше шагов при кросс-зональных запросах.
- **Связанные ТЗ**: все.

### DEC-010: MVP-транспорт client↔server — HTTP JSON на фиксированном порту

- **Дата**: 2026-05-28
- **Статус**: Accepted
- **Контекст**: нужен рабочий мультиплеер для учебного MVP без сложного стека.
- **Решение**:
    - Транспорт: `stdlib` HTTP (`ThreadingHTTPServer` на сервере, `urllib` на клиенте).
    - Порт по умолчанию: `8765`.
    - Сервер bind: `0.0.0.0` (LAN + localhost); клиент подключается по IP/hostname.
    - Синхронизация: клиент poll `GET /api/matches/{id}/sync`; сервер authoritative tick loop.
- **Альтернативы**: WebSocket; gRPC; peer-to-peer.
- **Последствия**:
    - плюс: простой отладочный MVP, без лишних зависимостей;
    - минус: polling вместо push; не оптимально для продакшена.
- **Связанные ТЗ**:
    - `docs/specs/server/001.NIKITA.SERVER_MATCH_JOIN_AND_TICK_LOOP.md`
    - `docs/specs/client/001.NIKITA.CLIENT_PYGAME_CORE_AND_MATCH_UI.md`

### DEC-011: Формула цены рецепта — `time_coef` у каждого завода

- **Дата**: 2026-05-28
- **Статус**: Accepted
- **Контекст**: в `GAME_TECH_REQUIREMENTS` цена зависит от времени производства; нужно уточнить, где хранить коэффициент.
- **Решение**: `buildings.time_coef` per `building_type`; формула при `price_override IS NULL`:
  `sum(ingredient.base_sell_price × amount) + production_time_sec × buildings.time_coef`.
- **Альтернативы**: один глобальный `time_coef`; коэффициент в каждом рецепте.
- **Последствия**:
    - плюс: разные заводы балансируются независимо;
    - минус: при добавлении завода нужен seed для `buildings`.
- **Связанные ТЗ**: `docs/specs/db/001.NIKITA.SQLITE_SCHEMA_AND_SEED_MINIMAL.md`
