# TZ REQUIREMENTS

## 1) Назначение

Этот документ фиксирует единый стандарт подготовки ТЗ в проекте `Farm Wars`.

Цели стандарта:

- сделать ТЗ однозначными и проверяемыми,
- минимизировать недопонимания между разработчиками,
- обеспечить корректную работу ИИ-агента по checkpoint-модели,
- поддержать параллельную разработку без блокировок.

Связанные обязательные документы процесса:

- `DECISIONS.md` — журнал принятых архитектурных/процессных решений,
- `TASK_STATUS.md` — актуальный статус выполнения ТЗ и checkpoint-ов.

---

## 2) Где хранить ТЗ

- Все ТЗ хранятся в `docs/specs/<section>/`.
- `<section>` выбирается по зоне задачи:
    - `architecture`
    - `client`
    - `server`
    - `network`
    - `db`
    - `engine_cpp`
    - `gameplay`

---

## 3) Формат имени файла ТЗ

Обязательный формат:

`{NNN}.{DEVELOPER}.{TITLE}.md`

Где:

- `NNN` — трехзначный индекс (`001`, `002`, ...),
- `DEVELOPER` — один из:
    - `NIKITA`
    - `SANYA`
    - `NIKITA_LEAD`
- `TITLE` — краткое имя задачи в `UPPER_SNAKE_CASE` на латинице.

Примеры:

- `001.NIKITA.CLIENT_LOBBY_FLOW.md`
- `002.SANYA.CPP_TICK_ENGINE_BASE.md`
- `003.NIKITA_LEAD.NETWORK_CONTRACT_V1.md`

Правила индексации:

- нумерация ведется отдельно внутри каждой секции,
- номер не переиспользуется даже при удалении файла.

---

## 4) Обязательная структура ТЗ

Каждое ТЗ обязано содержать следующие разделы:

1. `Context`
2. `Goal`
3. `Scope`
4. `Functional Requirements`
5. `Non-Functional Requirements`
6. `Data Contracts / API Contracts`
7. `Implementation Plan`
8. `Checkpoints`
9. `Acceptance Criteria`
10. `Test Plan`

Если хотя бы один раздел отсутствует, ТЗ считается недействительным.

---

## 5) Требования к содержанию разделов

## `Context`

- Кратко описывает текущую ситуацию в кодовой базе.
- Указывает, почему задача нужна именно сейчас.

## `Goal`

- Формулируется измеримо.
- Должно быть ясно, что считать завершенным результатом.

## `Scope`

- Явно разделяется:
    - что входит,
    - что не входит.

## `Functional Requirements`

- Список функциональных требований с конкретным поведением системы.
- Требования должны быть проверяемыми.

## `Non-Functional Requirements`

- Ограничения по платформе, стабильности, совместимости, UX-отклику и т.п.

## `Data Contracts / API Contracts`

- Описываются форматы входа/выхода.
- Обязательны ключевые поля, типы и ограничения.
- Для межмодульных задач указывается версия контракта (`v1`, `v2`, ...).

## `Implementation Plan`

- Пошаговый план выполнения.
- Шаги должны быть реалистичными и независимыми по возможности.

## `Checkpoints`

- Для каждого checkpoint указать:
    - ожидаемый результат,
    - артефакт для демонстрации,
    - способ проверки,
    - условие приемки.

## `Acceptance Criteria`

- Четкий список условий "готово".
- Без размытых формулировок типа "работает нормально".

## `Test Plan`

- Минимальный набор проверок (ручных/авто), подтверждающих выполнение задачи.

---

## 6) Обязательные правила для межмодульных ТЗ

Если задача затрагивает больше одной зоны (`Python client/server`, `C++ engine`, `DB`), ТЗ должно включать:

1. `Contract-First` описание взаимодействий.
2. Минимум один fixture для входных данных.
3. План stub-реализации для недоступного соседнего модуля.
4. Отдельный checkpoint на интеграцию с реальным модулем.

Без этих пунктов межмодульное ТЗ не принимается.

---

## 7) Правила постановки ТЗ через ИИ-агента

Перед генерацией ТЗ ИИ-агент обязан:

1. Изучить релевантные файлы репозитория.
2. Задать все критичные уточняющие вопросы.
3. Дождаться ответов.
4. Только после этого сформировать ТЗ.

Критичные вопросы обязаны покрывать:

- границы задачи,
- исполнителя (`NIKITA` / `SANYA` / `NIKITA_LEAD`),
- зависимости и риски интеграции,
- контракты и критерии приемки.

---

## 8) Правила выполнения по checkpoints

- Работы ведутся последовательно по checkpoint.
- После каждого checkpoint исполнитель/ИИ-агент:
    - показывает результат,
    - указывает измененные файлы,
    - дает шаги локальной проверки,
    - запрашивает приемку.
- Переход к следующему checkpoint разрешен только после явного подтверждения.
- Не реже чем после каждого 1-2 технических checkpoint выполняется **общий командный checkpoint**:
    - каждый разработчик публикует краткий отчет в общей группе (`сделано / в работе / блокеры`),
    - каждый разработчик проводит взаимную проверку изменений другого разработчика,
    - результаты проверки фиксируются в сообщении (OK или список замечаний).
- После каждого принятого checkpoint обязательно обновляется строка задачи в `TASK_STATUS.md`.
- Если в ходе задачи принято новое архитектурное/процессное решение, оно фиксируется в `DECISIONS.md`.

---

## 9) Критерии качества ТЗ

Хорошее ТЗ:

- однозначное,
- измеримое,
- проверяемое,
- ограниченное по scope,
- не блокирует команду отсутствием "чужой" реализации,
- содержит явные контракты и артефакты приемки.

Плохое ТЗ:

- абстрактное ("улучшить", "оптимизировать" без метрик),
- не содержит API/данных,
- не разделяет in-scope/out-of-scope,
- не имеет checkpoints и критериев приемки.

---

## 10) Шаблон мини-проверки перед публикацией ТЗ

Перед сохранением ТЗ автор обязан ответить "Да" на все пункты:

- Указан корректный исполнитель в имени файла?
- Присутствуют все 10 обязательных разделов?
- Цель и критерии приемки измеримы?
- Есть границы scope (входит/не входит)?
- Для межмодульной задачи описаны контракт, fixture, stub?
- Checkpoints позволяют принимать работу поэтапно?
- ТЗ можно выполнять независимо от неготовности соседних модулей?

Если хотя бы один ответ "Нет", ТЗ дорабатывается.
