# GUIDE_FOR_AI

## 1) Назначение документа

Этот документ определяет стандарт поведения ИИ-агента, который работает в репозитории `Farm Wars`.

Цель:

- обеспечить предсказуемую и качественную работу ИИ по задачам команды,
- сохранить архитектурную целостность проекта,
- обучать разработчиков процессу постановки и исполнения задач через ИИ.

Базовые технические требования проекта находятся в `GAME_TECH_REQUIREMENTS.md`.  
Если есть противоречия, приоритет у `GAME_TECH_REQUIREMENTS.md`.

Обязательные операционные документы:

- `DECISIONS.md` — журнал принятых решений (почему и что выбрано),
- `TASK_STATUS.md` — общий трекер статусов ТЗ и checkpoint-ов.

---

## 2) Контекст проекта (обязательный для агента)

- Игра: 2D farm simulator с мультиплеером.
- Платформа: Windows desktop.
- Клиент и game loop: Python (`pygame`).
- Мультиплеер и серверная логика: Python.
- Ядро симуляции: C++ модуль, вызываемый из Python (`pybind11`).
- База данных: SQLite (нормализованная схема, FK).
- Главная цель команды: рабочая играбельность и обучение разработке с ИИ.

---

## 3) Роли команды (для маршрутизации задач)

- `NIKITA_LEAD`:
    - архитектура, контракты, интеграция, приемка.
- `NIKITA`:
    - Python client/server/network/db.
- `SANYA`:
    - C++ simulation core и Python bindings.

Если задача не содержит явного исполнителя, ИИ-агент обязан спросить, кому адресуется ТЗ:
`NIKITA`, `SANYA` или `NIKITA_LEAD`.

---

## 4) Главный рабочий цикл ИИ-агента

ИИ-агент обязан работать строго по шагам:

1. Получить идею задачи от разработчика.
2. Изучить релевантные файлы репозитория.
3. Задать все необходимые уточняющие вопросы (количество не ограничено).
4. Дождаться ответов на все критичные вопросы.
5. Сформировать ТЗ в правильном формате файла.
6. При реализации двигаться по checkpoints.
7. После каждого checkpoint остановиться и запросить приемку.
8. Только после подтверждения переходить к следующему checkpoint.
9. При изменении архитектурного/процессного выбора обновить `DECISIONS.md`.
10. После каждого checkpoint обновить прогресс в `TASK_STATUS.md`.

Запрещено:

- пропускать фазу вопросов перед генерацией ТЗ,
- молча менять архитектурные решения, влияющие на другие зоны,
- выполнять всю задачу “одним большим коммитом” без checkpoint-приемки.

---

## 5) Правила генерации ТЗ

### 5.1 Именование файлов

Формат обязателен:

`{NNN}.{DEVELOPER}.{TITLE}.md`

Где:

- `NNN` — трехзначный номер (`001`, `002`, ...),
- `DEVELOPER` — `NIKITA` | `SANYA` | `NIKITA_LEAD`,
- `TITLE` — короткое имя на латинице в `UPPER_SNAKE_CASE`.

Примеры:

- `001.NIKITA.CLIENT_LOBBY_FLOW.md`
- `002.SANYA.CPP_TICK_ENGINE_BASE.md`
- `003.NIKITA_LEAD.NETWORK_CONTRACT_V1.md`

### 5.2 Размещение ТЗ

ТЗ размещаются в `docs/specs/<section>/`, где `<section>` — тематический раздел:

- `client`,
- `server`,
- `network`,
- `db`,
- `engine_cpp`,
- `gameplay`,
- `architecture`.

### 5.3 Обязательные секции ТЗ

Каждый файл ТЗ обязан содержать:

- `Context`
- `Goal`
- `Scope`
- `Functional Requirements`
- `Non-Functional Requirements`
- `Data Contracts / API Contracts`
- `Implementation Plan`
- `Checkpoints`
- `Acceptance Criteria`
- `Test Plan`

---

## 6) Стандарт уточняющих вопросов от ИИ

Перед созданием ТЗ ИИ-агент должен проверить минимум:

- **Границы задачи**: что входит/не входит.
- **Исполнитель**: на кого оформляется задача.
- **Зависимости**: какие модули и чьи зоны затрагиваются.
- **Контракты**: какие входы/выходы, форматы данных и инварианты.
- **Приемка**: как понять, что результат принят.
- **Риски интеграции**: что может сломать соседние подсистемы.

Если в задаче не хватает данных по любому из пунктов, ИИ обязан спросить.

---

## 7) Стандарт checkpoint-приемки

Для каждого checkpoint в ТЗ должно быть явно указано:

- что именно реализуется,
- что должно быть показано для приемки,
- как это проверяется.

Дополнительно, не реже чем после каждого 1-2 технических checkpoint, обязателен **общекомандный checkpoint**:

- каждый разработчик отправляет в общую группу краткий статус-отчет (что сделано, что в работе, какие блокеры),
- каждый разработчик просматривает изменения другого разработчика и фиксирует замечания/подтверждение,
- только после этого команда переходит к следующему этапу.

После выполнения checkpoint ИИ-агент обязан отправить короткий отчет:

1. Что сделано.
2. Что изменено (файлы/контракты).
3. Как проверить локально.
4. Запрос явной приемки:  
   `Подтверди приемку checkpoint N, чтобы я продолжил.`

Без явной приемки переход дальше запрещен.

После приемки checkpoint ИИ-агент обязан:

- обновить статус соответствующей строки в `TASK_STATUS.md`,
- добавить короткую запись в журнал общекомандных checkpoint (если это командная синхронизация).

## 8) Архитектурные правила, которые нельзя нарушать

- Python владеет game loop и orchestration.
- Сервер авторитетен в мультиплеере.
- Клиенты отправляют команды, а не итоговое состояние.
- C++ модуль не должен напрямую управлять UI и сетью.
- Игровые сущности и рецепты должны быть декларативны (SQLite), а не захардкожены по возможности.
- Изменения контракта Python <-> C++ требуют обновления документации контракта и примера использования.
- Любая межмодульная задача реализуется по схеме `contract -> fixture -> stub -> real integration`.

---

## 9) Протокол изолированной разработки (без готовых тестовых данных)

Если разработчики работают параллельно и зависимый модуль еще не готов, ИИ-агент обязан:

1. Зафиксировать контракт взаимодействия:
    - входные/выходные структуры,
    - типы команд и событий,
    - версию контракта.

2. Создать минимальные fixtures:
    - минимум 1 позитивный сценарий,
    - минимум 1 пограничный сценарий.

3. Сгенерировать временный stub для отсутствующего соседа:
    - предсказуемый,
    - воспроизводимый,
    - с тем же интерфейсом, что и будущая реализация.

4. Оформить в ТЗ отдельный checkpoint:
    - `Contract Approved`,
    - `Fixtures Approved`,
    - `Stub Approved`,
    - `Real Integration Approved`.

5. Запретить зависимость "ждем чужой модуль":
    - если можно продолжить через stub/fixtures, ИИ должен продолжать.

---

## 10) Правила качества изменений

ИИ-агент должен:

- делать минимально необходимые изменения под задачу,
- не ломать существующие договоренности репозитория,
- добавлять понятные названия, а не аббревиатуры без смысла,
- оставлять код читаемым для новичков в команде,
- явно указывать команды запуска и проверки.

**Интеграционные тесты (без UI):** после изменений server/engine/MP — как минимум:

```bash
py tools/init_db.py --seed
py tools/test_server_flow.py
py tools/test_multiplayer.py
py tools/test_vertical_slice.py
```

Мультиплеер 2–4: спека `docs/specs/gameplay/009.NIKITA.MULTIPLAYER_2PLUS_VERIFICATION.md`.  
Перед `py tools/build_engine.py` на Windows — остановить `py -m server` и клиенты (блокировка `.pyd`).

ИИ-агент не должен:

- переписывать большие части проекта без запроса,
- менять чужие зоны без согласования,
- вносить “скрытые” архитектурные изменения.

---

## 11) Формат итогового отчета ИИ после выполнения задачи

После выполнения задачи ИИ-агент дает структурированный отчет:

1. `Result`
    - достигнута ли цель ТЗ.
2. `Changes`
    - ключевые файлы и что в них изменено.
3. `Verification`
    - как запускалось/проверялось.
4. `Limitations`
    - что не покрыто и почему.
5. `Next Step`
    - что логично делать следующим шагом.

Отчет должен быть коротким, конкретным и проверяемым.

Сначала изучи релевантные файлы и задай все необходимые уточняющие вопросы.
После моих ответов создай ТЗ в docs/specs/<section>/ с именем

Далее выполняй задачу строго по checkpoints: после каждого checkpoint

## 13) Критерий успешной работы ИИ в проекте

Работа ИИ считается качественной, если:

- задачи формализуются в понятные ТЗ,
- изменения проходят по checkpoint-приемке,
- архитектура не расползается между языками и слоями,
- разработчики могут легко продолжать работу после ИИ,
- команда реально учится процессу, а не только получает готовый код,
- работа не блокируется отсутствием "боевых" данных благодаря контрактам, fixtures и stubs.
